--- НАЧАЛО ДОКУМЕНТА ---

Философия проекта Damoony
10 ключевых принципов, на которых построен движок. Код и реализации старого проекта не переносились — переносились принципы и контракты.

⚠️ Честно: не все принципы соблюдаются в текущем коде. Где есть расхождение — это указано явно. Истина о фактическом поведении — MANIFEST.md §7. Этот документ — о намерениях.

1. Домен и Алиас — разделение инфраструктуры и контента
Всё вращается вокруг Домена и Алиаса. Домен — инфраструктура (настройки, привязки хостов, глобальные схемы и блоки). Алиас — контент (страницы, локальные схемы, переопределения блоков).
Следствие: DomainResolver как точка входа; никакого хардкода имён доменов; админка и файловая структура строго разделяют уровни.
Соблюдается: ✅ полностью. Это самый крепкий принцип проекта.

2. UI — это дерево, а не текст
Представление — типизированное дерево узлов (Node, Element, Attrs), а не строковый шаблон. Рендер — финальный шаг. Высокоуровневые элементы (формы, таблицы) — из базовых компонентов.
Следствие: никаких Twig/Blade; UI-слой — PHP-DOM с явными типами и XSS-экранированием на уровне атрибутов.
Соблюдается: ✅ в основном.
Расхождения:
- Builder неполон (нет table, form, section и т.д.) — сложные структуры через new Element() (§6.6).
- Node — контракт с изъяном: Text::append(), Slot::append() бросают LogicException. Разделение на Node / ParentNode — не сделано.

3. Регионы, слоты и Filler (Правило 3 файлов)
Шаблон домена — именованные регионы (блоки). Схема (каркас страницы) содержит слоты, в которые регионы вставляются. Иерархия схем: локальная алиаса → глобальная домена. Filler — переопределение региона для конкретного алиаса.
Следствие: регион — единица расширения. Ядро знает только о RegionInterface. Глобальные манифесты (blocks.json, schemes.json) удалены. Каждая сущность описывается тремя файлами: {name}.php, {name}.rules.json, {name}.editor.json.
Соблюдается: ✅ полностью. RegionRegistry (disabled → forcedGlobal → filler → base) работает образцово.
Расхождения:
- Slot::release() возвращает '' — слот без региона молча исчезает (диагностика через structure:check).

4. Роутинг — файловые правила
Страницы живут в файловой иерархии algoritm/ алиаса. Правила — .rules.json рядом. Роутер читает правила, идёт по сегментам URL, вызывает default(). Regex-параметры, флаг auth, namespace — часть контракта.
Следствие: никаких routes.php с сотнями строк. Конфигурация роутинга — данные, не код.
Соблюдается: ✅ полностью.
Ограничения:
- @preg_match в RulesMatcher глушит ошибки — битый regex даст тихий notFound, а не диагностику.
- RouteMatch::forbidden() — мёртвый код.

5. Low-Code и компиляция (Zero-Overhead)
Визуальный Drag&Drop оставлен ТОЛЬКО для Схем (HTML-каркасов). Админка сохраняет структуру схемы в editor.json и компилирует в {name}.php. 
Страницы, Блоки и Филлеры визуальных редакторов НЕ ИМЕЮТ (удалены ради безопасности). Они пишутся исключительно через CodeMirror (ручной PHP).
Следствие: мы убрали "магию" генерации кода для страниц, закрыв уязвимость RCE. Разработчик получает полный контроль над кодом.
Соблюдается: ✅ полностью (stage-5, stage-6).
Расхождения:
- Для генерации сырого PHP (блоки custom/if) требуется явный флаг security.allow_php_blocks=true (по умолчанию заблокировано).

6. Explicit over implicit
Никаких $GLOBALS, статических кэшей, магии __get, скрытых зависимостей. Всё передаётся явно через конструктор. Контейнер — удобство сборки, не источник состояния.
Следствие: класс без конструктора с зависимостями — ошибка проектирования.
Соблюдается: ✅ в основном.
Расхождения:
- assert() в prod исчезает — проверки типов из контейнера не выполняются (§6.3, P2).
- RegionContext::service(string): mixed — Service Locator (осознанный trade-off, §6.2).
- Главное противоречие §6.1 РЕШЕНО: теперь все страницы создаются как "голые" (только код), и разработчик явно вызывает SchemeRenderer, если ему нужен каркас.

7. Contract-first
Публичный API — интерфейсы (AuthInterface, RegionInterface, CommandInterface), не классы. Реализация — деталь. Каждый модуль — один публичный вход.
Следствие: расширение публичного API — только через новые интерфейсы.
Соблюдается: ✅ в основном.
Расхождения:
- RegionContext::service() возвращает mixed — контракт размыт (§6.2).
- AlgoritmInterface::default(): Node|Response|null разрешает null, но PageHandler::toResponse() на null возвращает 204 No Content (stage-4).

8. CLI-First (Единый источник истины)
Любая файловая операция (создание, удаление, компиляция) вызывается через CLI (bin/cli.php).
Админка — это "тонкий клиент". Она рендерит HTML и вызывает CLI-команды (например, SchemeRemoveCommand). 
AI-агенты используют безопасный фасад bin/aicli.php, который тоже вызывает CLI.
Следствие: бизнес-логика не дублируется. Любое изменение в CLI мгновенно отражается в админке и доступно агентам.
Соблюдается: ✅ полностью. Это архитектурный фундамент проекта.

9. Безопасность — не фича, а основа
Пароли — только password_hash. CSRF на всех POST. Удаление — только через POST. Загрузки — whitelist. Сессии — HttpOnly, SameSite. Safe Mode и строгий CSP.
Удалены визуальные редакторы страниц и блоков (защита от RCE). Доступ к AI-агенту ограничен Whitelist-ом в aicli.php.
Следствие: никаких phpinfo(), GET-удалений, паролей в открытом виде, выполнения сырого PHP из UI.
Соблюдается: ✅ в основном. Все P0 закрыты.

10. Диагностика и отказоустойчивость
Система сама подсказывает разработчику, что сломано. StructureChecker проверяет наличие всех 3 файлов (.php, .rules.json, .editor.json) для каждого элемента, стыковку блоков и схем. Есть System Health, Safe Mode.
Следствие: System Health, structure:check, structure:repair.
Соблюдается: ✅ в основном.
Расхождения:
- Safe Mode работает на уровне bootstrap админки, но ошибки внутри контроллеров ловит Kernel (500, не Safe Mode) — это ожидаемо.
