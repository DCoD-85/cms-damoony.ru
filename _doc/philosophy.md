# Философия проекта Damoony

Документ фиксирует принципы, на которых построен новый движок. Код и реализации старого проекта не переносятся — переносятся принципы и контракты.

---

## 1. Домен и Алиас — разделение инфраструктуры и контента

Всё в проекте вращается вокруг домена и алиаса. Домен — это инфраструктура (настройки, привязки, глобальные схемы, глобальные блоки). Алиас — это контент (конкретные страницы, локальные схемы, переопределения блоков). 

Следствие: движок обязан иметь `DomainResolver` как точку входа и не хардкодить имена доменов. Админка и файловая структура строго разделяют эти два уровня.

## 2. UI — это дерево, а не текст

Представление строится как типизированное дерево узлов (`Node`, `Element`, `Attrs`), а не как строковый шаблон. Рендер — финальный шаг, не источник истины. Высокоуровневые элементы (формы, таблицы) собираются из базовых компонентов (`Component`, `Field`, `Table`).

Следствие: никаких Twig/Blade. UI-слой — PHP-DOM с явными типами и XSS-экранированием на уровне атрибутов.

## 3. Регионы, слоты и Filler

Шаблон домена состоит из именованных регионов (блоков). Схема (каркас страницы) содержит слоты, в которые эти регионы вставляются. Иерархия схем: локальная схема алиаса -> глобальная схема домена. Filler — это переопределение региона для конкретного алиаса. Управление регионами доступно прямо из кода страницы.

Следствие: регион — единица расширения. Ядро не знает о конкретных регионах, знает только о контракте `RegionInterface`.

## 4. Роутинг — файловые правила

Страницы живут в файловой иерархии `algoritm/` конкретного алиаса. Правила — в `.rules.json` рядом. Роутер читает правила, идёт по сегментам URL, вызывает `default()`. Regex-параметры, флаг `auth`, namespace домена — часть контракта.

Следствие: никакого `routes.php` с сотнями строк. Конфигурация роутинга — данные, не код.

## 5. Один способ сделать что-то

Один слой БД (PDO), один файловый роутер, один автозагрузчик (Composer PSR-4), один способ сборки UI. Если появляется второй способ — первый удаляется или помечается `#[Deprecated]`.

Следствие: строгая архитектура без дублирования логики.

## 6. Explicit over implicit

Никаких `$GLOBALS`, статических кэшей, магических методов `__get` на критичных объектах, скрытых зависимостей. Всё, что нужно — передаётся явно через конструктор. Контейнер — удобство сборки, не источник состояния.

Следствие: класс без конструктора с зависимостями считается ошибкой проектирования.

## 7. Контракт-first

Публичный API — интерфейсы (`AuthInterface`, `RegionInterface`, `CommandInterface`), не классы. Реализация — деталь. Каждый модуль имеет один публичный вход и не более.

Следствие: расширение публичного API происходит только через новые интерфейсы.

## 8. CLI и Админка — равноправные интерфейсы

Любая операция (создание домена, страницы, управление блоками) доступна как через CLI-команды, так и через визуальный интерфейс Админки. Админка использует те же UI-компоненты, что и фронтенд, и включает встроенный редактор кода. 

Следствие: Админка — это не просто «просмотрщик», а полноценный инструмент управления.

## 9. Безопасность — не фича, а основа

Пароли — только `password_hash`/`password_verify`. CSRF-токены обязательны на всех POST-запросах. Удаление данных — только через POST и с подтверждением. Загрузки файлов — whitelist расширений. Сессии защищены HttpOnly и SameSite.

Следствие: никаких уязвимостей вроде `phpinfo()`, GET-удалений или паролей в открытом виде.

## 10. Идемпотентность и откат

Операции, меняющие состояние (`*:new`, `*:sync`, `*:extract`), должны быть идемпотентны. Разрушительные операции (удаление домена, алиаса) выполняются через карантин (rename в trash) с возможностью отката при ошибке конфига. Мутации конфигов — под lock, атомарно.

Следствие: `*:remove` без карантина или возможности отката считается багом.

## Стек нового движка

- PHP 8.4
- Composer (PSR-4, PSR-3, PSR-11)
- PHPUnit 10+
- PHPStan (level 8)
- PDO (SQLite dev / MySQL prod)
- Nginx + PHP-FPM (или Apache + mod_php)
