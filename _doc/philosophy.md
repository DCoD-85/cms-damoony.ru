--- НАЧАЛО ДОКУМЕНТА ---

Философия проекта Damoony
10 ключевых принципов, на которых построен движок. Код и реализации старого проекта не переносились — переносились принципы и контракты.

⚠️ Честно: не все принципы соблюдаются в текущем коде. Где есть расхождение — это указано явно. Истина о фактическом поведении — MANIFEST.md §7. Этот документ — о намерениях, не о текущем состоянии.

1. Домен и Алиас — разделение инфраструктуры и контента
Всё вращается вокруг Домена и Алиаса. Домен — инфраструктура (настройки, привязки хостов, глобальные схемы и блоки). Алиас — контент (страницы, локальные схемы, переопределения блоков).

Следствие: DomainResolver как точка входа; никакого хардкода имён доменов; админка и файловая структура строго разделяют уровни.

Соблюдается: ✅ полностью. Это самый крепкий принцип проекта.

2. UI — это дерево, а не текст
Представление — типизированное дерево узлов (Node, Element, Attrs), а не строковый шаблон. Рендер — финальный шаг. Высокоуровневые элементы (формы, таблицы) — из базовых компонентов.

Следствие: никаких Twig/Blade; UI-слой — PHP-DOM с явными типами и XSS-экранированием на уровне атрибутов.

Соблюдается: ✅ в основном.
Расхождения:

Attrs::release() не валидирует имена атрибутов → XSS-вектор (MANIFEST.md §7.2 п.2, P1).

Builder неполон (table, form, section и т.д. отсутствуют) — сложные структуры через new Element() (§6.6).

Node — контракт с изъяном: Text::append(), Slot::append() бросают LogicException. Разделение на Node / ParentNode — не сделано.

3. Регионы, слоты и Filler
Шаблон домена — именованные регионы (блоки). Схема (каркас страницы) содержит слоты, в которые регионы вставляются. Иерархия схем: локальная алиаса → глобальная домена. Filler — переопределение региона для конкретного алиаса. Управление регионами — из кода страницы.

Следствие: регион — единица расширения. Ядро знает только о RegionInterface.

Соблюдается: ✅ в RegionRegistry (приоритет: disabled → forcedGlobal → filler → base — образцовый).
Расхождения:

SchemeLoader всегда возвращает fallback, если схемы нет — нарушает инвариант «скрытых дефолтов нет» (§6.5, P1).

blocks.json записывается, но не читается; .data.php блоков не читаются (§4).

Slot::release() возвращает '' — слот без региона молча исчезает.

4. Роутинг — файловые правила
Страницы живут в файловой иерархии algoritm/ алиаса. Правила — .rules.json рядом. Роутер читает правила, идёт по сегментам URL, вызывает default(). Regex-параметры, флаг auth, namespace — часть контракта.

Следствие: никаких routes.php с сотнями строк. Конфигурация роутинга — данные, не код.

Соблюдается: ✅ полностью.
Ограничения:

@preg_match в RulesMatcher глушит ошибки — битый regex даст тихий notFound, а не диагностику.

RouteMatch::forbidden() и guest — мёртвый код.

5. Low-Code и компиляция (Zero-Overhead)
Визуальный редактор — инструмент генерации данных. Админка сохраняет структуру блоков в .edit.json. PageCompiler/RegionCompiler компилируют JSON в чистый PHP с Builder. Пользователь получает нативный PHP без парсинга JSON на лету.

Следствие: удобство конструктора (как Tilda/Webflow) без потери производительности.

Соблюдается: ✅ в основном. P0-блокеры закрыты (stage-1, 2a).
Расхождения:

~~addslashes вместо var_export~~ — ✅ закрыто (stage-1).

~~SchemeCompiler использует str_replace~~ — ✅ закрыто (stage-1).

~~Два формата .edit.json без миграции~~ — ✅ закрыто (stage-2a, legacy блокируется).

SchemeController::edit() схлопывает вложенные схемы (§6.15, P1).

Ручные страницы не идут через схему — визуальная и ручная версия одной страницы выглядят по-разному (§6.1).

6. Explicit over implicit
Никаких $GLOBALS, статических кэшей, магии __get, скрытых зависимостей. Всё передаётся явно через конструктор. Контейнер — удобство сборки, не источник состояния.

Следствие: класс без конструктора с зависимостями — ошибка проектирования.

Соблюдается: ✅ в основном.
Расхождения:

assert() в prod исчезает — проверки типов из контейнера не выполняются (§6.3, P2).

RegionContext::service(string): mixed — Service Locator (осознанный trade-off, §6.2).

FrontController создаёт Translator/LanguageNegotiator вручную, минуя контейнер (§6.19, P2).

Главное противоречие: ручные страницы не идут через схему, визуальные — идут. Пользователь не знает о разнице. Это противоположность explicit (§6.1, P1).

7. Contract-first
Публичный API — интерфейсы (AuthInterface, RegionInterface, CommandInterface), не классы. Реализация — деталь. Каждый модуль — один публичный вход.

Следствие: расширение публичного API — только через новые интерфейсы.

Соблюдается: ✅ в основном.
Расхождения:

RegionContext::service() возвращает mixed — контракт размыт (§6.2).

AlgoritmInterface::default(): Node|Response|null разрешает null, а runtime на null бросает RuntimeException → 500. Контракт противоречит поведению (§6.18, P1).

8. CLI и Админка — равноправные интерфейсы
Любая операция доступна как CLI, так и через админку. Админка использует те же UI-компоненты, что фронтенд, и включает CodeMirror. AI-агенты управляют через CLI, люди — через UI.

Следствие: админка — полноценный инструмент, не «просмотрщик».

Соблюдается: 🟡 частично.
Расхождения:

«100% паритет CLI/UI» — неверно. Только CLI: db:migrate, vars:extract, trash:clear, user:new. Только UI: CodeMirror, визуальные редакторы, профиль, управление банами (MANIFEST.md §3).

Админка и CLI делят бизнес-логику (через *NewCommand, *ToggleCommand) — это плюс, и он реально работает.

9. Безопасность — не фича, а основа
Пароли — только password_hash/password_verify. CSRF на всех POST. Удаление — только через POST и с подтверждением. Загрузки — whitelist. Сессии — HttpOnly, SameSite. Safe Mode и строгий CSP.

Следствие: никаких phpinfo(), GET-удалений, паролей в открытом виде.

Соблюдается: ✅ в основном. P0 закрыты (stage-2b, stage-3).
Расхождения:

~~CSRF на destructive GET~~ — ✅ закрыто (stage-2b).

~~Response::internalError($e->getMessage()) в PageHandler~~ — ✅ закрыто (stage-3, в prod generic).

XSS на именах атрибутов в Attrs::release() (§7.2 п.2, P1).

Что работает: password_hash, CSRF на POST, HttpOnly, RateLimit, CSP, Safe Mode, whitelist загрузок, hash_equals — это сильная сторона проекта.

10. Диагностика и отказоустойчивость
Система сама подсказывает разработчику, что сломано. StructureChecker проверяет стыковку схем, блоков и страниц. Ошибка в одном алиасе не роняет сайт и админку. Есть System Health, structure:check, Safe Mode.

Следствие: System Health, structure:check, Safe Mode.

Соблюдается: 🟡 частично.
Расхождения:

StructureChecker не ловит .edit.json ↔ PHP, legacy .edit.json, blocks.json ↔ папки, schemes.json ↔ файлы («сироты» вроде visuo.data.php) (§7.2 п.3, P1).

Safe Mode работает на уровне bootstrap админки, но ошибки внутри контроллеров ловит Kernel (500, не Safe Mode) — это ожидаемо.

«Белых экранов нет» — ✅ соблюдается. Kernel ловит Throwable.
